# theCliniQ Phase 5 Step 3 — Appointment Intent & Slot Reservation decision matrix

| Decision | Rationale | Invariant / constraint | Consequence |
| --- | --- | --- | --- |
| Boundary | Step 3 stops at `APPOINTMENT_INTENT → SLOT_RESERVED`. | No payment state, appointment, or provider call is created. | Step 4 owns payment handoff. |
| Intent | An intent records a patient-authorized request, not a confirmed appointment. | Patient account, booking actor, provider XOR, Offering/version, price snapshot, local request, timezone, UTC interval, state, expiry, idempotency are immutable after reservation. | Appointment lifecycle remains separate. |
| Provider | Exactly one doctor or clinic provider is snapshotted from the Offering owner. | `provider_doctor_profile_id XOR provider_clinic_id`; supplied IDs never authorize. | Doctor-to-Doctor is prohibited. |
| Service/version/price | Use an active applicable immutable Offering version and its immutable price. | FKs plus copied currency/minor-unit/version snapshot; no mutable current price. | Future Phase 4 allocation has stable input. |
| Capacity identity | Initial canonical capacity identity is `service_offering_version_id`. | Reservation capacity is counted only within that immutable version and UTC interval. | Cross-service/provider shared pools are deferred; an Offering cannot claim an unimplemented shared pool. |
| Reservation | `slot_reservations` is short-lived capacity consumption linked one-to-one to intent. | Status `HELD`, `RELEASED`, `EXPIRED`; only unexpired `HELD` consumes capacity. | No generated-slot table is required. |
| Concurrency | PostgreSQL is sole authority. | Lock the version/configuration capacity parent `FOR UPDATE`, re-evaluate availability and live holds, insert reservation in one transaction. | Capacity 1 permits one concurrent success; capacity 2 permits two. |
| Expiry | Hold lifetime is a validated, versioned Service Offering Version configuration in integer seconds. | `expires_at = reservation_created_at + configured_hold_seconds`; expiry is immutable, and `expires_at <= current_timestamp` never consumes capacity. | No universal hard-coded hold duration; worker is optional cleanup only and late events cannot resurrect expiry. |
| Authorization | Reuse Phase 2 session, membership, network, and permission boundaries. | Patient→Doctor/Clinic requires provider eligibility, active Offering/version, explicit service exposure, availability, lead/horizon, and patient authorization; no network is required. Clinic→Doctor requires active bilateral `BOOK`; Clinic→Clinic uses later referral model; DISCOVER/CONTACT never book. | IDs and clinic context never grant access or implicitly expose a doctor-owned service. |
| Time | Client local request is converted once using validated provider IANA timezone and Step 2 rules. | Server derives UTC boundaries from local request, duration, buffers, lead/horizon, recurrence/exceptions. | DST spring gaps reject/skip; fall ambiguity uses earlier occurrence. |
| Idempotency | Every creating mutation has DB-backed key and request fingerprint. | Unique `(booking_actor_account_id, idempotency_key)`; same fingerprint returns original result, differing fingerprint conflicts. | Concurrent retries cannot reserve twice. |
| States | Intent: `APPOINTMENT_INTENT`, `SLOT_RESERVED`, `EXPIRED`, `CANCELLED`; reservation: `HELD`, `RELEASED`, `EXPIRED`. | Transition guard prevents reverse/illegal transitions. | No `PAYMENT_PENDING` in Step 3. |
| Reschedule | Schema permits a successor intent/reservation relationship. | Future transaction acquires new hold before releasing old hold using ordered locks. | Existing reservation is never lost on failed replacement. |
| Audit | Reuse `audit_events`; no generic event table is needed initially. | Audit creation, denial, idempotency conflict, hold/release/expiry; metadata has IDs/outcome only. | `appointment_intent_events` is unnecessary. |
| Retention | Intents/reservations are retained, never hard-deleted by normal lifecycle. | Restrictive FKs; lifecycle timestamps and audit preserve evidence. | Future legal retention policy can extend without rewriting facts. |
| Financial handoff | Snapshot price/version only. | No allocation, payment intent, webhook, refund, ledger, or settlement writes. | Step 4 converts a valid hold into payment processing. |
| Non-goals | No slots, payment, UI, Redis authority, assignment/publication, tenant-specific doctor schedules. | No schema/API bypass for these scopes. | Scope remains reversible and controlled. |
